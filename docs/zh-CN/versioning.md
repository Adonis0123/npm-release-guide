# 该选哪个版本号

最后核实：2026-11-24

这一页讲怎么决定一次版本号升级（Version Bump），以及这个选择会怎样影响安装你包的人。不用把规则背下来：平时直接让 Agent 用 `npm-version-guide` 判断，想核对原因时再翻这一页。

## 三个数字各代表什么

正式版本号是三个非负整数，不能带前导零，写作 `主版本号.次版本号.修订号`（`MAJOR.MINOR.PATCH`）[F-73], [F-74]。每一位按数值递增，例如 `1.9.0` 后面是 `1.10.0` [F-74]。这套规范叫做语义化版本 2.0.0（SemVer）[F-83]。

- **PATCH（修订号）**（`1.2.3` → `1.2.4`）：向下兼容的问题修复 [F-73]。
- **MINOR（次版本号）**（`1.2.3` → `1.3.0`）：向下兼容的新功能 [F-73]，或把对外接口（Public Interface）里的某项标为弃用 [F-79]。
- **MAJOR（主版本号）**（`1.2.3` → `2.0.0`）：对对外接口做了破坏性变更（Breaking Change）[F-73]。

**对外接口（Public Interface）**指用 `your-package` 的人能依赖的一切：入口、命令、参数、默认值、输出格式和支持的 Node.js 版本。**破坏性变更（Breaking Change）**指更新后，一部分老用户必须改自己的代码或配置才能继续用。

已经发布的版本内容绝不能改动；任何修改都必须发成新版本 [F-75]。

## 按改动判断升哪一位

下表适用于 `1.0.0` 及以上版本（`0.x` 看下一节）。一次发布包含多项改动时，按最高那一档升。

| 这次改了什么 | 升哪一位 | 原因 |
| --- | --- | --- |
| 删掉一个参数或命令 | MAJOR | 还在用它的老用户会报错 [F-73] |
| 改了默认值 | MAJOR | 依赖旧默认值的老用户行为会变 [F-73] |
| 改了输出格式 | MAJOR | 读取旧格式的脚本或程序会失效 [F-73] |
| 提高最低 Node.js 版本要求 | MAJOR | 按本指南对对外接口的定义，停在旧版 Node.js 的用户跑不起来 `your-package` |
| 修了 bug，但改变了老用户已经依赖的行为 | MAJOR | 按本指南对对外接口的定义，就算旧行为原本是 bug，让调用方失效也算破坏性变更 |
| 新增功能或参数（旧的还能用） | MINOR | 向下兼容的新功能 [F-73] |
| 把某个参数标为弃用，准备以后删 | MINOR | SemVer 要求弃用升 MINOR，真正删除留到后面的 MAJOR [F-79] |
| 修 bug，且不影响现有调用方 | PATCH | 向下兼容的问题修复 [F-73] |
| 更新内部依赖，对外接口不变 | PATCH 或 MINOR | 兼容改动；修问题升 PATCH，加功能升 MINOR [F-81] |
| 只改文档、注释或测试 | 不用升 | 不影响版本号，除非同时包含破坏性变更 [F-100], [F-103] |

## `0.x` 版本怎么算

SemVer 规定 `0.y.z` 处于开发初始阶段，一切都可能随时改变 [F-76], [F-83]。规范里的 MINOR 和 PATCH 规则只针对 `1.0.0` 及以上版本；SemVer 本身并没有“在 `0.x` 里破坏性变更升 MINOR”这条规定 [F-76]。

npm 的版本库（`node-semver`）沿用了这个习惯：它的脱字符规则把 `0.x` 的 MINOR 当成破坏性变更信号，并默认 `0.2.4` → `0.2.5` 不会破坏调用方 [F-96]。因为 `^0.2.3` 会自动装上 `0.2.4` 但不会装上 `0.3.0` [F-94]，`node-semver` 指出在 `0.x` 阶段用 MINOR 表示破坏性变更很常见 [F-96]；`conventionalcommits` 预设也可以按选项把新功能降为升 PATCH [F-102]。

## 什么时候发 `1.0.0`

起步版本号上，SemVer 和 npm 的建议不同：

- SemVer 常见问题建议从 `0.1.0` 起步，之后每次发布升 MINOR [F-77]。
- npm 官方语义化版本文档建议直接从 `1.0.0` 起步 [F-84]。

如果你从 `0.x` 起步，SemVer 常见问题说：一旦 `your-package` 用在生产环境、用户开始依赖稳定的对外接口，或者你开始担心兼容性，就应该到 `1.0.0` 了 [F-78]。

## 预发布版本（Pre-release）和发布标签（Release Tag）

**预发布版本（Pre-release）**在修订号后面加短横线和点分标识，例如 `1.2.0-beta.1` 或 `1.2.0-rc.1` [F-82]。它的优先级低于对应的正式版本（`1.2.0-rc.1 < 1.2.0`），也不必保证与正式版相同的兼容性 [F-82]。

默认情况下，`npm publish` 会把 `latest` **发布标签（Release Tag）**指向新版本，而普通 `npm install your-package` 装的就是 `latest` [F-88]。为了不让普通用户误装预发布版本，发布时要指定别的发布标签，例如 `next`：

- **npm 11 及以上**：不传 `--tag`（也没配 `publishConfig.tag` 或 `--force`）时，`npm publish` 会直接拒绝发布预发布版本 [F-90]。
- **npm 10**：没有这项检查，不传 `--tag` 发布预发布版本可能会把 `latest` 指过去 [F-88]（据 npm 10 源码推断，未实测 [F-90]）。
- **暂存发布（Staged Release）**同样如此：标签在暂存时就定死了，预发布版本也必须带 `--tag` [F-53]。

用 `next`、`beta` 这类普通词当发布标签都可以；除了 `latest`，npm 对其他标签名没有特殊含义 [F-88]。不要起像版本范围的名字（例如 `v1.4`），npm 会拒绝 [F-89]。

用 `npm version` 把预发布版本转正式版时，对 `1.2.0-5` 跑 `npm version patch` 只会去掉后缀变成 `1.2.0`，不会跳到 `1.2.1` [F-85]。

## 发错了版本怎么办

已发布的版本不能覆盖 [F-75]。按情况选下面三种做法之一：

1. **发一个新版本修复（通常首选）。** 如果不小心把破坏性变更发成了 MINOR，SemVer 建议再发一个新的 MINOR 恢复兼容，并告诉用户哪个版本有问题 [F-80]。如果要给旧的主版本分支发修复（例如发完 `2.0.0` 后再发 `1.4.1`），npm 11 要求带上 `--tag`，防止覆盖 `latest` [F-91]。
2. **用 `npm deprecate` 给安装的人弹提示。** `npm deprecate your-package@1.2.0 "请改用 1.2.1"` 会向所有安装该版本的人显示警告 [F-92]。它支持单个版本或版本范围（范围会包含预发布版本），只有包所有者能执行，传空字符串 `""` 可以撤掉警告 [F-92]。
3. **撤回（unpublish）只作最后手段。** 在公共 npm 仓库上，发布后 72 小时内撤回要求没有其他公开包依赖 `your-package`；超过 72 小时还必须满足上周下载量少于 300 次且只有一个所有者 [F-93]。用过的 `your-package@版本号` 永远不能再用，撤回无法撤销，删光全部版本后 24 小时内不能发新版本 [F-93]。大多数情况下 npm 建议用 `npm deprecate` [F-93]。

## `^` 和 `~` 决定用户会自动装上哪些版本

别人运行 `npm install your-package` 时，npm 默认在他们的 `package.json` 里写入脱字符 `^` 范围 [F-98]。这个符号决定了你以后发的新版本会不会自动到他们手里：

| 用户 `package.json` 里的范围 | 实际匹配范围 | 会自动收到 |
| --- | --- | --- |
| `^1.2.3` | `>=1.2.3 <2.0.0-0` [F-94] | PATCH 和 MINOR（`1.2.4`、`1.3.0`），不含 `2.0.0` |
| `^0.2.3` | `>=0.2.3 <0.3.0-0` [F-94] | 仅 PATCH（`0.2.4`），不含 `0.3.0` [F-94]（实测 npm 10.9.9 也是这样表现 [F-110]） |
| `^0.0.3` | `>=0.0.3 <0.0.4-0` [F-94] | 不会自动更新 |
| `~1.2.3` | `>=1.2.3 <1.3.0-0` [F-95] | 仅 PATCH（`1.2.4`），不含 `1.3.0` |
| `~0.2.3` | `>=0.2.3 <0.3.0-0` [F-95] | 仅 PATCH（`0.2.4`），不含 `0.3.0` |

注意上限末尾的 `-0`：`^1.2.3` 也不会匹配 `2.0.0-alpha.1` [F-94]。普通范围只有在同一个 `MAJOR.MINOR.PATCH` 上本身写了预发布标签时才匹配预发布版本，所以 `^1.2.3` 永远不会自动拉取 `1.3.0-beta.1` [F-97]（实测 npm 10.9.9 也是这样表现 [F-110]）。

## 为什么本指南用 `npm version` 加 git 标签

Changesets、`release-please` 这类工具适合一个仓库里联动发布多个包的场景。本指南保留 `npm version` 加 `v*` 标签 [F-86], [F-87]，因为配置更简单：在 GitHub Actions 里，用内置 `GITHUB_TOKEN` 推上去的标签不会触发其他工作流 [F-104]（`release-please-action` 因此需要额外配个人访问令牌 [F-105]；`changesets/action` 除非另传 `github-token`，默认使用 GitHub 提供的令牌，但其标签是否同样无法触发工作流未经 Changesets 官方证实，只是根据 [F-104] 推断 [F-106]），而且 Changesets 暂不支持暂存发布 [F-107]。

## 关于日历版本（CalVer）

日历版本把发布日期放进版本号，刻意不传达破坏性变更 [F-108]；带前导零的日期（如 `2026.01.05`）不是合法的 SemVer [F-109]（实测 npm 10.9.9 也是这样表现 [F-110]），而且 npm 默认的 `^` 范围仍会把跳动的日期段当成主版本号或次版本号变化来算 [F-109]。

卡住了：问你的 Agent“下个版本该升哪个号？用 npm-version-guide 看看。”
