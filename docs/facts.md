# Facts

Every claim the guide makes about npm, its CLI and related tools, with a first-hand source. Writers of the guide pages take facts from this file only.

Format: `- [F-xx] <fact> — Source: <URL> — Quote: "<verbatim quote>" — Verified: <date>`. A fact without an official source carries `Status: OBSERVED (<where>)` or `Status: UNCONFIRMED`. Quotes are copied from the page text; code formatting (backticks) is dropped. Terms follow `GLOSSARY.md`.

Versions at verification time: npm CLI latest tags `v12.2.3` and `v11.21.3` (docs.npmjs.com labels the v11 pages "Legacy"; CLI command pages below are cited at v12, and the v11 pages had the same text for every quoted sentence).

## Trusted Publishing

- [F-01] Trusted Publishing supports three CI providers: GitHub Actions (GitHub-hosted runners), GitLab CI/CD (GitLab.com shared runners) and CircleCI (CircleCI cloud). Self-hosted runners are not supported. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "Self-hosted runners are not currently supported but are planned for future releases." — Verified: 2026-11-24
- [F-02] Trusted Publishing needs npm CLI 11.5.1 or later and Node.js 22.14.0 or later in the workflow. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "Trusted publishing requires npm CLI version 11.5.1 or later and Node version 22.14.0 or higher." — Verified: 2026-11-24
- [F-03] A new Trusted Publishing link expires if the workflow does not publish successfully within 2 days; an expired link cannot be edited and must be deleted and recreated. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "A newly created trusted publisher configuration must complete its first successful publish within 2 days." — Verified: 2026-11-24
- [F-04] The package setting "Require two-factor authentication and disallow tokens" blocks Access Tokens only; Trusted Publishing keeps working, and npm recommends turning the setting on after Trusted Publishing is set up. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "Your trusted publishers will continue to work normally, as they use OIDC tokens." — Verified: 2026-11-24
- [F-05] Trusted Publishing can only be attached to a package that already exists on the registry. This is stated on the `npm trust` page; the trusted-publishers page does not say it. — Source: https://docs.npmjs.com/cli/v12/commands/npm-trust — Quote: "The package you're configuring must already exist on the npm registry." — Verified: 2026-11-24
- [F-06] `npm trust` needs npm 11.15.0 or later (not 11.5.1), write access to the package, 2FA enabled on the account, and does not accept an Access Token with Bypass 2FA or username/password auth. — Source: https://docs.npmjs.com/cli/v12/commands/npm-trust — Quote: "Granular Access Tokens (GAT) with the bypass 2FA option are not supported." — Verified: 2026-11-24
- [F-07] `npm trust github [package] --file <workflow.yml> --repo <owner/repo> [--env <name>] --allow-publish and/or --allow-stage-publish` creates the link from the command line; at least one `--allow-*` flag is required. `--repo` falls back to `repository.url` in `package.json`. — Source: https://docs.npmjs.com/cli/v12/commands/npm-trust — Quote: "At least one of these flags is required when creating a trust configuration." — Verified: 2026-11-24
- [F-08] `npm trust list [package]` shows the link and its id; `npm trust revoke [package] --id=<id>` removes it. The first `npm trust` request asks for a Second Factor; the browser page offers to skip 2FA for the next 5 minutes for follow-up commands. — Source: https://docs.npmjs.com/cli/v12/commands/npm-trust — Quote: "The first request will require two-factor authentication." — Verified: 2026-11-24
- [F-09] Conflict between two npm pages: the `npm trust` page says one Trusted Publishing link per package, the trusted-publishers page says up to 10. — Source: https://docs.npmjs.com/cli/v12/commands/npm-trust — Quote: "Currently, the registry only supports one configuration per package." — Verified: 2026-11-24 — Counter-source: https://docs.npmjs.com/trusted-publishers — Quote: "Each package can have up to 10 trusted publishers configured at the same time" — Status: UNCONFIRMED (which limit applies today)
- [F-10] Each Trusted Publishing link has "allowed actions". `npm stage publish` is always allowed; links created after Sep 03, 2026 allow only staging by default, and direct `npm publish` must be ticked separately. Existing links cannot be edited, only deleted and recreated. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "Configurations created after Sep 03, 2026 are automatically set to allow" — Verified: 2026-11-24
- [F-11] The GitHub workflow needs `permissions: id-token: write`, and `repository.url` in `package.json` must exactly match the GitHub repository. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "must exactly match your GitHub repository" — Verified: 2026-11-24
- [F-12] npm does not check the Trusted Publishing settings when they are saved; a wrong workflow filename shows up only at publish time as `ENEEDAUTH` ("Unable to authenticate"). All fields are case-sensitive. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "npm does not verify your trusted publisher configuration when you save it." — Verified: 2026-11-24
- [F-13] Trusted Publishing works only for `npm publish`, `npm stage publish` and `npm dist-tag`; `npm stage approve/reject/list/view` need the Publisher in person, and `npm whoami` does not test Trusted Publishing. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "require interactive authentication and cannot use OIDC tokens, as these actions require proof of presence" — Verified: 2026-11-24
- [F-14] Provenance is added automatically, without `--provenance`, when all of these hold: publishing through Trusted Publishing, from a public repository, for a public package. CircleCI and private repositories get no Provenance. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "This automatic generation only applies when all of these conditions are met:" — Verified: 2026-11-24
- [F-15] A private repository gets no Provenance even when the package is public. — Source: https://docs.npmjs.com/trusted-publishers — Quote: "Provenance generation is not supported for private repositories, even when publishing public packages." — Verified: 2026-11-24

## Access Tokens

- [F-16] Only granular Access Tokens exist; legacy (classic) tokens are gone. The docs say "November 2025", but the final revocation happened on 2025-12-09 (F-17). — Source: https://docs.npmjs.com/about-access-tokens — Quote: "As of November 2025, only Granular access tokens are supported. Legacy access tokens have been removed." — Verified: 2026-11-24
- [F-17] All classic tokens were permanently revoked on 2025-12-09 and cannot be recreated or recovered. — Source: https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ — Quote: "We’ve permanently revoked all existing npm classic tokens." — Verified: 2026-11-24
- [F-18] Write Access Tokens are capped at 90 days. The docs pages give no number (only "at least one day in the future"); the cap comes from the changelog. — Source: https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ — Quote: "write tokens limited to 90 days maximum" — Verified: 2026-11-24
- [F-19] The 7-day default lifetime for new write Access Tokens comes only from an announcement of a plan "starting in mid-October" 2025; no later page confirms it. The `npm token` page says the server picks the default. — Source: https://github.blog/changelog/2025-09-29-strengthening-npm-security-important-changes-to-authentication-and-token-management/ — Quote: "A default expiration of seven days, reduced from 30 days." — Verified: 2026-11-24 — Status: UNCONFIRMED (current default; https://docs.npmjs.com/cli/v12/commands/npm-token says "If not specified, the server will determine the default expiration.")
- [F-20] "Bypass two-factor authentication" is an option on write Access Tokens, off by default; when on, it overrides account and package 2FA settings for publishing. — Source: https://docs.npmjs.com/about-access-tokens — Quote: "The Bypass 2FA capability applies to tokens with write access and is set to false by default at token creation." — Verified: 2026-11-24
- [F-21] Since August 2026 a Bypass-2FA Access Token can no longer change 2FA, manage tokens, add or remove maintainers, or do org/team management; those need an interactive Second Factor. — Source: https://docs.npmjs.com/about-access-tokens — Quote: "Starting August 2026, tokens with Bypass 2FA enabled can no longer be used to perform account-identity or account-governance actions." — Verified: 2026-11-24
- [F-22] The 2026-07-31 changelog also lists changing Trusted Publishing configuration among the actions a Bypass-2FA token lost, and announces that such tokens will lose direct publishing, targeted for January 2027. — Source: https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/ — Quote: "We are targeting January 2027 for this update." — Verified: 2026-11-24
- [F-23] The docs state the January 2027 removal of direct publishing with Access Tokens as a fact, not a target. — Source: https://docs.npmjs.com/about-access-tokens — Quote: "The ability to publish new package versions directly with a granular access token will be removed in January 2027." — Verified: 2026-11-24
- [F-24] Since 2026-09-18 an Access Token can be "Read and write (stage only)": it can run `npm stage publish` but `npm publish` fails with `E_STAGE_REQUIRED`, even with Bypass 2FA on. It keeps other write rights such as moving dist-tags. Existing tokens are unchanged. — Source: https://github.blog/changelog/2026-09-18-stage-only-npm-tokens-for-safer-automation/ — Quote: "This release is opt-in and doesn’t change existing tokens or their direct-publish capabilities." — Verified: 2026-11-24
- [F-25] Conflict between npm pages on creating granular tokens from the CLI: the creating-tokens page says it is not possible, while the `npm token` page documents `npm token create` with `--bypass-2fa`, `--expires` and `read-write-stage-only`, and the 2025-12-09 changelog announces the CLI support. — Source: https://docs.npmjs.com/creating-and-viewing-access-tokens — Quote: "You cannot create granular access tokens from the CLI currently." — Verified: 2026-11-24 — Counter-source: https://docs.npmjs.com/cli/v12/commands/npm-token — Quote: "setting this to true will allow the token to bypass two-factor authentication" — Status: UNCONFIRMED (the creating-tokens page looks outdated)

## Package publishing access and `npm access`

- [F-26] The package "Publishing access" setting has two choices: "Require two-factor authentication or a granular access token with bypass 2fa enabled" (default for new packages) and "Require two-factor authentication and disallow tokens" (recommended). — Source: https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification — Quote: "This is the default option for all new packages." — Verified: 2026-11-24
- [F-27] With "Require two-factor authentication and disallow tokens", no Access Token can publish, whatever its Bypass 2FA setting; every publish needs a Second Factor. — Source: https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification — Quote: "Granular access tokens cannot be used to publish packages, regardless of their bypass 2FA setting." — Verified: 2026-11-24
- [F-28] `npm access set mfa=none|publish|automation [<package>]` sends these fields: `none` → `publish_requires_tfa=false`; `publish` → `publish_requires_tfa=true, automation_token_overrides_tfa=false`; `automation` → `publish_requires_tfa=true, automation_token_overrides_tfa=true`. The docs page lists the syntax but does not explain the values. — Source: https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/workspaces/libnpmaccess/lib/index.js#L68-L87 (tag v12.2.3) — Quote: "// tfa is required, automation tokens cannot override tfa" — Verified: 2026-11-24
- [F-29] Likely mapping to the web labels: `mfa=publish` ≈ "Require two-factor authentication and disallow tokens", `mfa=automation` ≈ the default "…or a granular access token with bypass 2fa enabled". The field name says "automation token", a removed token type; no npm page confirms the mapping or that it also blocks Bypass-2FA granular tokens. `mfa=none` has no matching web choice, since npm now requires 2FA for all packages. — Source: https://docs.npmjs.com/requiring-2fa-for-package-publishing-and-settings-modification — Quote: "All packages now require two-factor authentication (2FA) or a granular access tokens with bypass 2FA enabled for creating and publishing packages." — Verified: 2026-11-24 — Status: UNCONFIRMED (mapping and whether mfa=none is still accepted)

## Second Factor (2FA)

- [F-30] Account 2FA has two modes: "authorization and writes" (default; Second Factor for login, profile and token changes, and for publish, unpublish, deprecate, access changes) and "authorization only" (login, profile and token changes only). CLI names: `auth-and-writes`, `auth-only`. — Source: https://docs.npmjs.com/about-two-factor-authentication — Quote: "By default, 2FA is enabled for authorization and writes." — Verified: 2026-11-24
- [F-31] No fetched npm page contains the settings label "Require two-factor authentication for write actions"; that it equals `auth-and-writes` is an inference from the mode names. — Status: UNCONFIRMED (label not found in docs.npmjs.com pages checked)
- [F-32] A Passkey ("security key") can be used on the web and in the CLI but can only be set up on the website. — Source: https://docs.npmjs.com/configuring-two-factor-authentication — Quote: "Security-key with WebAuthn can be used for authentication from both the web and the command line, but it can only be configured from the web." — Verified: 2026-11-24
- [F-33] `npm profile enable-2fa` sets up an OTP authenticator: the CLI expects an `otpauth://` URL from the registry and shows a QR code. — Source: https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/lib/commands/profile.js#L312-L320 (tag v12.2.3) — Quote: "Expected otpauth URL" — Verified: 2026-11-24
- [F-34] Recovery codes are given when 2FA is turned on and can be viewed or regenerated later on the 2FA settings page; each code works once. Logging in with one puts a 72-hour hold on the account: no publishing, no token creation, no settings changes. The hold cannot be lifted early. — Source: https://docs.npmjs.com/configuring-two-factor-authentication — Quote: "Using a recovery code to log in triggers a temporary 72-hour security hold on your account." — Verified: 2026-11-24
- [F-35] `npm profile get` prints the 2FA line as just the mode (`auth-and-writes`, `auth-only` or `disabled`); the CLI code has no field that tells Passkey from OTP. `--json` prints the raw registry object, which may hold more. — Source: https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/lib/commands/profile.js#L98-L130 (tag v12.2.3) — Quote: "cleaned[tfa] = info.tfa.mode" — Verified: 2026-11-24 — Status: UNCONFIRMED (whether the registry's JSON distinguishes Passkey from OTP)

## Login Session and Browser Confirmation

- [F-36] `npm login` uses Browser Confirmation by default (`auth-type` default `web`); passing an `otp` value forces the old `legacy` username/password flow. — Source: https://docs.npmjs.com/cli/v12/using-npm/config — Quote: "Note that if an otp config is given, this value will always be set to legacy." — Verified: 2026-11-24
- [F-37] `npm login --auth-type=web` prints "Authenticate your account at:" with a link, and pressing ENTER opens the browser. — Source: https://docs.npmjs.com/accessing-npm-using-2fa — Quote: "npm 8.14.0 and higher support login flow through the browsers." — Verified: 2026-11-24
- [F-38] Since 2025-12-09 `npm login` creates a Login Session instead of a long-lived token; the changelog says it lasts two hours. Sessions are not listed among tokens. — Source: https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ — Quote: "These sessions automatically expire after two hours, requiring reauthentication to continue publishing." — Verified: 2026-11-24
- [F-39] An npm staff member wrote on 2025-12-18 that the Login Session was extended to 12 hours from 2025-12-12. No changelog or docs page states this. — Source: https://github.com/community/community/discussions/179562#discussioncomment-15292325 — Quote: "we've extended the session to 12 hours" — Verified: 2026-11-24 — Status: UNCONFIRMED (staff forum comment only; no changelog or docs page)
- [F-40] The `npm login` docs page still says it creates a legacy token, which conflicts with F-16 and F-38. — Source: https://docs.npmjs.com/cli/v12/commands/npm-login — Quote: "the CLI automatically generates a legacy token of" — Verified: 2026-11-24 — Status: UNCONFIRMED (page looks outdated)
- [F-41] npm publishes no lifetime for the Browser Confirmation link. The CLI keeps polling the registry with no limit of its own, waiting as long as the registry's `Retry-After` header says. — Source: https://github.com/npm/npm-profile/blob/v13.0.1/lib/index.js#L115-L133 — Quote: "const retry = +res.headers.get('retry-after') * 1000" — Verified: 2026-11-24 — Status: UNCONFIRMED (link lifetime)
- [F-42] In one test the Browser Confirmation link stopped working about 95 seconds after it was printed; opening it later gave `E404`. — Status: OBSERVED (one manual run, 2026)

## How the npm CLI asks for a Second Factor

- [F-43] `npm publish` (and `npm login` with `auth-type=legacy`) asks for a Second Factor through the `otplease` helper; `npm stage publish` skips it on purpose (see https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/lib/commands/publish.js#L205-L215, comment "Stage intentionally bypasses otplease"). When the registry asks for a Second Factor and stdin or stdout is not a terminal (an Agent's shell, CI), npm does not ask; it fails with the registry's error (`EOTP`, "OTP required for authentication"). — Source: https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/lib/utils/auth.js#L6-L33 (tag v12.2.3; same code in v11.21.3) — Quote: "if (!process.stdin.isTTY || !process.stdout.isTTY) {" — Verified: 2026-11-24
- [F-44] In a Real Terminal, if the `EOTP` reply contains both `authUrl` and `doneUrl`, npm prints "Authenticate your account at" and waits for Browser Confirmation. — Source: https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/lib/utils/auth.js#L14-L23 (tag v12.2.3) — Quote: "if (err.code === 'EOTP' && err.body?.authUrl && err.body?.doneUrl) {" — Verified: 2026-11-24
- [F-45] Otherwise (an `EOTP` without those links, or an `E401` mentioning a one-time password) npm prints "This operation requires a one-time password." and "Enter OTP:". — Source: https://github.com/npm/cli/blob/cfd03796843cc9ae26c7034ab99bae6c002a4ba4/lib/utils/auth.js#L25-L29 (tag v12.2.3) — Quote: "This operation requires a one-time password." — Verified: 2026-11-24
- [F-46] The CLI sends its `auth-type` setting to the registry as the `npm-auth-type` request header. — Source: https://github.com/npm/npm-registry-fetch/blob/v20.0.1/lib/index.js#L219-L221 — Quote: "headers['npm-auth-type'] = opts.authType" — Verified: 2026-11-24
- [F-47] When a Passkey-only Publisher in a Real Terminal still gets "Enter OTP" is not documented. Likely cases (inferred from F-36, F-45, F-46, F-58): the registry seems to choose between browser links and a plain OTP request based on the `npm-auth-type` header, so `auth-type=legacy`, a preset `otp` value, or a registry reply without browser links would lead to "Enter OTP". An older npm page (last edited 2023) shows a legacy flow where the browser shows a generated code that the Publisher pastes at "Enter one-time password:". — Source: https://docs.npmjs.com/accessing-npm-using-2fa — Quote: "Copy the generated token" — Verified: 2026-11-24 — Status: UNCONFIRMED (no current source for when a Passkey-only Publisher sees "Enter OTP")

## Staged Release

- [F-48] Staged publishing became generally available on 2026-05-22. — Source: https://github.blog/changelog/2026-05-22-staged-publishing-and-new-install-time-controls-for-npm/ — Quote: "Staged publishing is now generally available on npm." — Verified: 2026-11-24
- [F-49] Staged publishing needs npm CLI 11.15.0 or later, Node.js 22.14.0 or later, publish access, and 2FA on the account. — Source: https://docs.npmjs.com/staged-publishing — Quote: "Staged publishing requires npm CLI version 11.15.0 or later and Node version 22.14.0 or higher." — Verified: 2026-11-24
- [F-50] `npm stage publish` uploads without a Second Factor; `npm stage approve <stage-id>` (or Approve in the Staged Packages tab on npmjs.com) needs one; `npm stage list`, `view` and `download` let the Publisher inspect first. — Source: https://docs.npmjs.com/staged-publishing — Quote: "You will be prompted for 2FA verification whether you approve the package in the CLI or on npmjs.com." — Verified: 2026-11-24
- [F-51] Staging works for a brand-new package name. npm then publishes a public placeholder version `0.0.0-stage` until the staged version is approved. — Source: https://docs.npmjs.com/staged-publishing — Quote: "When you stage a package that does not yet exist, npm publishes a placeholder version of the package with the version" — Verified: 2026-11-24
- [F-52] In one First Release a `0.0.0-stage` version was visible for about 3 minutes. — Status: OBSERVED (one First Release of a new package, 2026)
- [F-53] A staged version's dist-tag is fixed at staging time; pre-release versions need an explicit `--tag`, as with `npm publish`. — Source: https://docs.npmjs.com/cli/v12/commands/npm-stage — Quote: "The tag is an immutable property of the staged package." — Verified: 2026-11-24

## Other package managers

- [F-54] pnpm reads npm's `~/.npmrc`, so an npm Login Session or token also works for `pnpm publish` against the same registry. — Source: https://pnpm.io/npmrc — Quote: "so credentials you set up for npm keep working" — Verified: 2026-11-24
- [F-55] `pnpm publish` accepts `--otp` (or `PNPM_CONFIG_OTP`), prompts for an OTP when the registry asks, and prints a link with a QR code when the registry asks for Browser Confirmation. Under Trusted Publishing it adds Provenance on its own. — Source: https://pnpm.io/cli/publish — Quote: "If the registry requests web-based authentication, pnpm will print a scannable QR code along with the URL." — Verified: 2026-11-24
- [F-56] `yarn npm login` (Yarn Berry) asks for username, password and OTP and writes the token to Yarn's own configuration in the home folder; whether Yarn also reads npm's `.npmrc` is not stated on these pages. It has `--web-login` for login only; `yarn npm publish` documents `--otp`, `--provenance` and `--staged`. — Source: https://yarnpkg.com/cli/npm/login — Quote: "This command will ask you for your username, password, and 2FA One-Time-Password" — Verified: 2026-11-24 — Status: UNCONFIRMED (whether yarn npm publish supports Browser Confirmation)
- [F-57] Yarn v1 and v2 used a legacy login endpoint that npm restored only temporarily in December 2025 and plans to remove. — Source: https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/ — Quote: "This endpoint primarily affects users of Yarn v1 and v2." — Verified: 2026-11-24
- [F-58] `bun publish` reads `.npmrc` and `bunfig.toml`, uses Browser Confirmation by default (`--auth-type web`), supports `--auth-type legacy` and `--otp`, and respects `NPM_CONFIG_TOKEN`. — Source: https://bun.com/docs/pm/cli/publish — Quote: "tells the npm registry which method you prefer" — Verified: 2026-11-24
- [F-59] `bun publish` cannot create Provenance; asking for it is an error. — Source: https://bun.com/docs/pm/cli/publish — Quote: "cannot generate provenance statements yet" — Verified: 2026-11-24

## Observed while publishing (no official source)

These come from real publishing runs in 2026. Pages must present them as observations, not npm rules.

- [F-62] Running `npm whoami` or `npm publish` without a Login Session failed with `E401 Unauthorized`; `npm login` fixed it. — Status: OBSERVED (two manual runs, 2026-11)
- [F-63] A GitHub environment deployment rule created through `gh api` without `type=tag` was stored as a branch rule; with a branch rule, pushing a `v*` tag cannot use the environment. Adding the rule with `type=tag` and pattern `v*` worked. — Status: OBSERVED (2026-11-24)
- [F-64] A handoff script that piped npm's output through `| tee` still failed with `EOTP` in a Real Terminal; removing the pipe brought back the Browser Confirmation link. — Status: OBSERVED (two runs, 2026-11)
- [F-65] Opening the Browser Confirmation link in a browser that was not logged in to npm showed the npm login page instead of the approval page, and the link expired before the Publisher could finish. Opening it in the Publisher's own logged-in browser worked. — Status: OBSERVED (2026-11-23)
- [F-66] For a package whose folder had both `README.md` and `README.zh-CN.md`, the npm package page showed the Chinese file. A publish step that told npm to use `README.md` as the readme fixed it. — Status: OBSERVED (two packages, 2026)
- [F-67] With one security key already registered, the two-factor settings page still showed the "Add Security Key" button under the list of keys, so a second Passkey can be added as a backup. — Status: OBSERVED (2026-11-24, settings page screenshot)
